# 城市公共设施线索研判系统

市民上传文字和现场照片后，系统提取设施故障、位置和紧急等级，建议主责部门，并将同一故障的多次上报关联到一个事件。管理员可以在同一页面核对原图、确认派单，并从研判简报追溯到每条原始线索。

例如，两位市民先后报告同一编号的井盖缺失，后台会保留两份上报证据，并为该事件生成一张主工单。附近人行道上的断枝会单独建档，交由园林部门研判。

## 快速开始

需要 **Node.js 24** 和拥有本仓库读取权限的 GitHub 账号。基础服务使用 Node.js 内置的 HTTP 服务和 SQLite，可以直接启动。

```bash
git clone https://github.com/sam2006-bot/AgentSystem_wzx.git
cd AgentSystem_wzx
node server.mjs
```

1. 在运行服务的电脑上打开 [市民上报页](http://127.0.0.1:4317/)，填写问题描述或上传照片。补充路口方位、门牌或设施编号，或勾选「附带当前定位」，都有助于查重。
2. 打开 [管理员工作台](http://127.0.0.1:4317/admin)，使用首次启动时生成的 `data/admin-key.txt` 中的口令登录。
3. 在事件详情中核对证据，确认类型、位置、部门和紧急等级后派单。在「简报收件箱」选择统计时段，即可生成并查阅简报。

Windows 用户也可双击 [启动脚本](启动.cmd)。服务默认仅监听本机，工单和简报都保存在本地。正式接入市级平台时，需要配置当地职责清单和工单接口。

## 四个 Agent 如何协作

[编排层](orchestrator.mjs)登记了每个 Agent 的职责和输入输出，并按「线索解析 → 归属研判 → 重复合并 → 入库」的顺序处理每条上报。每个 Agent 输出统一的 `{result, confidence, evidence, method}`，即结论、置信度、依据和判断方法。编排层把各步结果记入该线索的「研判过程」，管理员在事件详情中逐条查看。

| Agent | 输入与判断 | 管理员看到的结果 |
| --- | --- | --- |
| 线索解析 | 从中文描述和图像证据中提取故障、位置（路口、门牌、地标或道路）、设施编号及风险，拆分一条上报中的多个明确问题，并识别「已经修好了」「不是井盖的问题」等否定表述 | 结构化事项、紧急等级、原文和原图 |
| 归属研判 | 先查设施养护台账，再按故障类型匹配市政、城管或园林职责 | 主责部门建议、匹配依据或待复核标记 |
| 重复合并 | 综合设施编号、位置描述、照片（原图指纹和感知哈希）、坐标和上报间隔打分 | 唯一强匹配自动关联，疑似重复附相似度和依据交人工合并；误合并可拆分，操作保留记录 |
| 简报生成 | 统计时段内的线索、事件、部门分布，与上一等长时段对比；列出地点分布、主要问题类型、超时未派单或未办结的事件，以及紧急事项的依据和处置建议 | 研判摘要和统计明细，带事件入口；服务还会为已结束且有上报的日期补生成日报 |

解析、路由和查重默认使用可检查的规则。后台队列每五秒刷新一次，值班人员可在生成简报前看到紧急事件。

### 文本模型（可选）

将 `TEXT_MODEL` 设为本机 Ollama 中的文本模型名称后，两个环节会调用模型：

- **线索解析**：规则无法确定问题类型或位置时，才请模型补充。模型只能从已知问题类型中选择；返回的位置必须能在原文中找到，否则丢弃。模型推断的类型、位置或紧急等级会标出，管理员确认之后才能派单。规则能确定的线索不调用模型。
- **简报生成**：模型从当期事件中选取最多三项重点。程序逐项核对编号、位置和故障类型，使用生成简报时的事件记录填写正文和统计。模型给出的字段错配、编号未知或重复时，收件箱采用模板摘要并记录原因。

视觉模型未能指出可见故障时，原图和观察结果保留为待核图。仅附地址的照片交由管理员确认，市民另行描述的故障仍可独立研判。

模型调用失败或超时，都会回退到规则结果。未配置模型时，系统完全按规则运行。

超时督办的时限在 [config.json](config.json) 的 `sla` 中设置，单位为小时。各问题类型的处置建议在 `rules` 的 `advice` 字段中设置。

### 查重规则

同类型的在办事件按以下证据打分，各项证据按「1 − ∏(1 − 单项分)」合成相似度：

| 证据 | 单项分 |
| --- | --- |
| 设施编号相同 | 1.00 |
| 同一张原图（SHA-256） | 0.95 |
| 照片感知哈希差异 ≤ 6 / ≤ 12 位 | 0.85 / 0.40 |
| 位置描述一致且为精确点位（门牌、路口方位、地标出入口、第几盏灯） | 0.70 |
| 同一路口同一方位 / 同一门牌 | 0.70 / 0.65 |
| 同一路口、同一地标（缺少方位或出入口） | 0.40 |
| 坐标相距 ≤ 20 / 50 / 150 米（双方精度均在 50 米以内） | 0.70 / 0.45 / 0.20 |
| 位置描述一致但范围较大（如只写路名） / 仅道路相同 | 0.25 / 0.15 |
| 24 小时内 | 0.10 |

- 相似度达到 0.70、事件在 7 天内有更新且只有一个这样的事件时，自动关联。多个事件同时达标时，设施编号相同的优先；仍无法区分时交人工合并。
- 门牌、方位、道路、地标或出入口明确不同的，直接视为不同事件。新线索要和事件中每条线索的位置都比对。
- 位置描述与坐标相距超过 300 米（另加双方定位精度）时，只列为疑似，不自动合并。设施编号相同时仍以编号为准。
- 坐标优先取照片 EXIF 中的 GPS，其次取市民勾选的浏览器定位。一条上报含多个不同位置时不使用坐标。感知哈希由市民端浏览器解码图片后计算，用于识别重新压缩或缩放后的同一张照片。

## 图片分析（可选）

基础服务可以接收并保存原图。Windows 上可使用系统 OCR 提取可见文字。需要根据照片场景给出故障候选时，可选择以下方式：

- **本地 CLIP 分类**。使用带 pip 的 Python 3.12，在项目根目录运行 `python vision/setup.py`。脚本下载固定版本的模型和分词器，将依赖安装到 `data/vision/`。之后可在 CPU 上离线推理。图像分类结果保留为待核实候选，管理员可查看原图并纠正类型。[模型与权重](https://huggingface.co/Xenova/clip-vit-base-patch32)
- **Ollama 视觉模型**。启动本机 Ollama 服务并安装支持图像输入的模型，将 `VISION_MODEL` 设为该模型名称后再启动本项目。系统优先使用模型返回的观察结果，调用失败时回退到本地分类、OCR 或人工核图。配置远程 `OLLAMA_URL` 会将上传图片发送至该地址。[Ollama 视觉接口](https://docs.ollama.com/capabilities/vision)

## 配置和数据

| 配置 | 默认值或位置 | 用途 |
| --- | --- | --- |
| `PORT` | `4317` | 本机 HTTP 端口 |
| `DATA_DIR` | `./data/` | SQLite 业务数据库和自动生成的管理员口令 |
| `ADMIN_KEY` | 首次启动时自动生成 | 通过环境变量指定管理员口令 |
| `VISION_MODEL` | 未设置 | 启用指定的 Ollama 视觉模型 |
| `TEXT_MODEL` | 未设置 | 启用指定的 Ollama 文本模型，用于补充线索解析和选取简报重点事件 |
| `OLLAMA_URL` | `http://127.0.0.1:11434` | Ollama 服务地址 |

在 [config.json](config.json) 的 `assets` 中可按设施编号设置养护部门，例如 `{"L-023": "市政"}`。修改职责规则或台账后重启服务。原始照片、工单、简报和操作记录存储在业务数据库中。本地数据目录、管理员口令、模型缓存和环境变量文件已加入 Git 忽略清单。

## 测试与验收

在项目根目录运行自动化测试。测试使用独立数据库，其中 [parse.test.mjs](test/parse.test.mjs) 和 [dedup.test.mjs](test/dedup.test.mjs) 覆盖口语化描述的解析和多信号查重，[orchestrator.test.mjs](test/orchestrator.test.mjs) 用模拟的模型服务覆盖编排、模型补充和简报研判。

```bash
node --test
```

也可以在空数据库中提交以下三条线索，验证跨 Agent 的处理结果。

| 现场描述 | 发生位置 | 设施编号 |
| --- | --- | --- |
| 机动车道井盖缺失 | 人民路与建设路交叉口东侧 | J-017 |
| 机动车道井口敞开 | 人民路与建设路交叉口东侧 | J-017 |
| 断枝悬挂在人行道上方 | 人民路与建设路交叉口西侧 | 留空 |

覆盖提交时段的简报应显示 **3 条上报、2 个独立事件、1 条补充事项**。市政事件关联前两条上报，园林事件关联第三条；对同一事件重复确认派单只会得到一张主工单。
